# Proving a change

Each stage catches what the previous one cannot see. Stages 3, 4, 6 and 8 apply to every lever; 1 and 2 when the lever adds decision logic; 5 and 7 when it lands through a pull request. Where merging needs the user's word, ask once, before stage 4, whether you may merge when the checks are green, so that the proof after the merge needs no second round trip.

1. **Local tests.** When the change adds decision logic (a skip, a mode switch), put it in pure functions and test them. Break the key condition on purpose: a mutant that passes the tests means the tests prove nothing, so add the case that turns it red.
2. **Live read-only trial.** For decision logic that reads an API, run it against the real API with a token scoped like the one the CI job receives (your own token is usually broader), in a temporary worktree of the target branch, and read what it decides. Run it again with a broken token: the fallback must take the full path.
3. **Static checks.** The repo's hooks, its typecheck and lint, a workflow linter on every changed workflow and action.
4. **Run on the branch.** Trigger the changed workflows on the branch before opening a pull request, to measure without merging. Before reading a cache number from a branch run, name the run that wrote the cache it restored, and whether the main branch's runs can read what this branch writes.
5. **Pull request.** Review the diff first. The body carries a before and after table with each number's conditions, the decisions, and what is left open.
6. **Wait on CI.** Where the harness watches CI and wakes you, let it. Otherwise watch with the provider CLI's watch command or poll the run API at a fixed interval, in the background. Stop on every terminal state (success, failure, cancelled, closed without merge) and on a timeout of twice the job's p90 duration plus its p90 queue time, since a job queued for a runner that never comes reaches no terminal state; then, after a merge, follow the runs it triggers.
7. **After the merge.** When the merge is yours to do, read the first run that the merge triggers: the cache published, the reuse count, the skip line naming the run it trusted. Otherwise the branch run gives the after numbers, and the first run after the merge becomes a follow-up. A lever whose proof spans days (bot rebase runs, hung and flaky jobs) gets its after number from a follow-up too. Put the numbers in the final before and after table.
8. **Report.** Per lever: before and after, in wall time and in runner minutes, each number with its conditions. Totals per change (all jobs one merge triggers) are estimates when built from single runs, and say so.
